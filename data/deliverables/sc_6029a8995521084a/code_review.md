# Code Review: PR #14661 - Replace fast_float C++ Library with Pure C Implementation

## Summary and Risk Assessment

PR #14661 replaces the bundled `deps/fast_float` C++ template library (3,838 lines in `deps/fast_float/fast_float.h` plus `deps/fast_float/fast_float_strtod.cpp`) with a single pure-C implementation (`src/fast_float_strtod.c`, ~360 lines of algorithmic code plus ~180 lines of tests). The motivation is clear: Redis should not require `g++` or `libstdc++` to build, since the project is written entirely in C and many target environments—especially embedded and minimal Linux distributions—lack the C++ toolchain. This PR eliminates every `g++-multilib`, `gcc-c++`, `g++-4.8`, and `g++` install step from CI workflows, removes `-lstdc++` from `FINAL_LIBS` in `src/Makefile`, deletes the entire `deps/fast_float/` directory, and adds `fast_float_strtod.o` directly to the `REDIS_SERVER_OBJ` list.

I assess this PR as **Medium risk**. The rationale: it replaces a core floating-point parsing path used by sorted-set score parsing, RESP double parsing, SORT BY scoring, and DEBUG SLEEP. Any correctness regression in float parsing could silently corrupt sorted-set orderings, break replication, or produce incorrect command results. However, the implementation uses a well-understood two-tier strategy (fast path for common cases, `strtod` fallback for edge cases) and includes a dedicated unit test with over 60 test cases. The risk is mitigated by the fact that the fallback path always calls the standard `strtod`, which is battle-tested. The primary concern is whether the fast path's boundary conditions and the new length-based API were applied correctly at all call sites.

The scope is broad: 19 files changed, spanning CI configuration (`.github/workflows/ci.yml`, `.github/workflows/daily.yml`), build infrastructure (`.gitignore`, `deps/Makefile`, `src/Makefile`), the core implementation (`src/fast_float_strtod.c`, `src/fast_float_strtod.h`), every call site (`src/debug.c`, `src/resp_parser.c`, `src/sort.c`, `src/t_zset.c`, `src/util.c`), and tests (`src/server.c`, `tests/unit/sort.tcl`). The net change is +600 lines added and -3,995 lines removed, a significant reduction in code size and complexity.

## Architecture and Design Review

The new implementation in `src/fast_float_strtod.c` uses a two-tier strategy that is architecturally sound for Redis's use case. The fast path, implemented in `parse_number_string()`, handles the common case where the mantissa fits in a `uint64_t` (≤ 2^53, defined as `MAX_MANTISSA_FAST_PATH`) and the exponent is within [-22, 22] (defined as `MIN_EXPONENT_FAST_PATH` and `MAX_EXPONENT_FAST_PATH`). This covers the vast majority of real-world floating-point values stored in Redis keys and sorted-set scores. When the fast path cannot handle a value—due to too many digits, an exponent outside the range, or non-decimal format—the function falls back to `fast_float_strtod_fallback()`, which copies the input into a null-terminated buffer and calls the standard `strtod()`.

The API change from `fast_float_strtod(const char *in, char **out)` (the old C++ wrapper in `deps/fast_float/fast_float_strtod.h`) to `fast_float_strtod(const char *nptr, size_t len, char **endptr)` (the new signature in `src/fast_float_strtod.h`) is a meaningful improvement. The old API required null-terminated strings, which forced every call site to either trust that the input was null-terminated or copy into a temporary buffer (as `zzlStrtod()` in `src/t_zset.c` did with a 128-byte stack buffer). The new API accepts an explicit length, allowing direct parsing of `sds` strings and RESP protocol fragments without allocation. This eliminates the copy-to-buffer pattern at multiple call sites and is more consistent with Redis's general preference for length-based string APIs.

The decision to move the implementation from `deps/fast_float/` to `src/` is appropriate. When the dependency was a 3,838-line C++ library requiring its own `Makefile` and `libfast_float.a`, a separate directory made sense. Now that the implementation is a single ~360-line C file, placing it in `src/` alongside other Redis source files eliminates an entire dependency build step and simplifies the build graph. The `DEPENDENCY_TARGETS` variable in `src/Makefile` no longer lists `fast_float`, and the link line no longer references `../deps/fast_float/libfast_float.a`.

One architectural concern: the fallback path in `fast_float_strtod_fallback()` uses a 128-byte `static_buf` and falls back to `zmalloc` for longer inputs. This introduces a Redis-specific allocator dependency (`zmalloc.h`) into what is otherwise a standalone parsing utility. If this file is ever reused outside Redis, the `zmalloc` call would need to be abstracted. For now, this is acceptable since the file is Redis-specific, but it should be noted in the file header.

## Call-Site Audit

**`src/debug.c` (DEBUG SLEEP):** The change is from `fast_float_strtod(c->argv[2]->ptr, NULL)` to `fast_float_strtod(c->argv[2]->ptr, sdslen(c->argv[2]->ptr), NULL)`. This is correct: `c->argv[2]->ptr` is an `sds` string, and `sdslen()` provides the accurate length. The new API will parse the duration value without requiring null-termination. No issues found.

**`src/resp_parser.c` (RESP double parsing):** The change removes the temporary `buf` array and the `memcpy`/null-termination step. Previously, the code copied `proto+1` into `buf` of size `MAX_LONG_DOUBLE_CHARS+1`, then called `fast_float_strtod(buf, NULL)`. Now it calls `fast_float_strtod(proto+1, len, NULL)` directly. The `len` variable is computed as `p-proto-1`, where `p` points to the `\r` delimiter. This correctly represents the length of the double string in the RESP protocol. The guard `if (len <= MAX_LONG_DOUBLE_CHARS)` remains, preventing excessively long inputs. This change eliminates an unnecessary copy and is correct.

**`src/sort.c` (SORT BY scoring):** The old code called `fast_float_strtod(byval->ptr, &eptr)` and then checked `eptr[0] != '\0'` to verify full consumption. The new code replaces this entire block with a call to `string2d(byval->ptr, sdslen(byval->ptr), &vector[j].u.score)`. This is a semantic change: instead of inline-parsing with the old API and checking `eptr` and `errno`, the code now delegates to the `string2d()` utility function. The `string2d()` function in `src/util.c` has itself been updated (see below), so this delegation is correct. However, the SORT test in `tests/unit/sort.tcl` adds a specific regression test for the smallest normal double `2.2250738585072012e-308`, which validates that this boundary value is handled correctly.

**`src/t_zset.c` (sorted-set range parsing and listpack scores):** Two patterns are updated. In `zslParseRange()`, the code now calls `fast_float_strtod((char*)min->ptr+1, len-1, &eptr)` for exclusive range bounds (prefixed with `(`) and `fast_float_strtod((char*)min->ptr, len, &eptr)` for inclusive bounds. The `len` is computed via `sdslen(min->ptr)`. For the exclusive case, `len-1` correctly accounts for skipping the `(` prefix. This is correct. In `zzlStrtod()`, the old code copied `vstr` into a 128-byte stack buffer and null-terminated it before calling `fast_float_strtod(buf, NULL)`. The new code calls `fast_float_strtod((char*)vstr, vlen, NULL)` directly, eliminating the copy. The `vlen` parameter is provided by `zzlGetScore()` from the listpack encoding. This is correct and more efficient.

**`src/util.c` (`string2d()`):** The old code called `fast_float_strtod(s, &eptr)` and, if the result did not consume the full input, fell back to `strtod(s, &fallback_eptr)` to handle hexadecimal strings (which `fast_float` did not support). The new code calls `fast_float_strtod(s, slen, &eptr)` and rejects the input if `eptr - s != slen`. This is a **behavioral change**: hexadecimal inputs like `0x10` are no longer accepted by `string2d()`. The new `fast_float_strtod()` implementation does parse `0x10` as `16.0` (as shown in the test case `{"0x10", 16.0}`), but this is handled by the `strtod` fallback path, not the fast path. However, since `string2d()` now rejects any input not fully consumed by `fast_float_strtod()`, and the fast path in `parse_number_string()` does not recognize hexadecimal, `0x10` would fall through to `fast_float_strtod_fallback()` which calls `strtod()`. If `strtod` consumes all `len` characters, the result is accepted. This should work correctly for valid hexadecimal strings, but it is a subtle change in control flow that deserves careful testing.

## Edge-Case and Correctness Analysis

**Special values (inf, nan):** The `parse_infnan()` function in `src/fast_float_strtod.c` handles `inf`, `infinity`, `nan`, and `nan(n-char-seq)` with case-insensitive matching. It uses a `strcasecmp_3()` helper that leverages the `| 0x20` trick for ASCII letter comparison, which is correct for the target characters 'a'-'z'. The function correctly handles optional `+`/`-` prefixes and the optional `inity` suffix for `infinity`. For `nan(n-char-seq)`, it validates that characters inside parentheses are alphanumeric or underscore, matching the C standard's `nan(n-char-seq-opt)` specification. One edge case: the code checks `if (remaining == 8 && strncasecmp_local(p, "inity", 5) == 0)` for the `infinity` suffix. This requires the total input to be exactly 8 characters (3 for `inf` + 5 for `inity`), which means inputs like `+infinity` (9 characters with sign) would not match the `inity` suffix. However, the sign is consumed before this check, so for `-infinity` the remaining after sign consumption is 8 characters—this is correct.

**Mantissa overflow:** The `parse_number_string()` function tracks digit count and rejects inputs with more than `MAX_DIGITS` (19) significant digits after skipping leading zeros. This is consistent with the fast_float C++ library's approach. The function uses `uint64_t` for the mantissa, and the fast path check `mantissa > MAX_MANTISSA_FAST_PATH` (2^53) ensures that only representable mantissas are converted directly. If the mantissa overflows during digit parsing (the `while` loops multiply by 10 or 100,000,000), the function still proceeds to the fast-path boundary check, which will reject the value and fall through to `strtod`. This is safe but could produce incorrect intermediate values; the final rejection based on the boundary check prevents any harm.

**strtod fallback path:** The `fast_float_strtod_fallback()` function copies the input into a null-terminated buffer (128-byte `static_buf` for small inputs, `zmalloc` for larger ones) and calls `strtod()`. The 128-byte threshold is a reasonable trade-off for avoiding allocation. The function correctly computes the `endptr` offset as `nptr + (fallback_end - buf)`, preserving the caller's coordinate space. One concern: if `zmalloc` fails (returns NULL), the code would crash. In practice, `zmalloc` in Redis aborts on allocation failure, so this is consistent with Redis's memory management philosophy. The fallback correctly sets `errno = EINVAL` when `strtod` fails to parse any characters.

**32-bit x86 extended-precision workaround:** The code includes a `volatile double ret = result; return ret;` pattern under `#if UINTPTR_MAX == 0xffffffff`. This forces the x87 FPU to store the result in a 64-bit memory slot and reload it, truncating 80-bit extended precision to IEEE 754 double precision. This is a well-known technique for avoiding precision-related bugs on 32-bit x86 with the x87 FPU. The comment explains the rationale clearly. This workaround is only applied to the fast path; the `strtod` fallback path already returns a properly-rounded `double`.

**SWAR digit parsing:** The `parse_eight_digits_swar()` function uses the SWAR (SIMD Within A Register) technique from the original fast_float library. The constants `0x000F424000000064ULL` and `0x0000271000000001ULL` match the original C++ implementation. The `is_made_of_eight_digits()` function uses the same bitmask trick. The `read8_to_u64()` function includes big-endian byte swapping, ensuring correctness on both little-endian and big-endian architectures.

## Build and CI Impact

The PR systematically removes all references to `g++`, `gcc-c++`, `gcc-4.8 g++-4.8`, `g++-multilib`, `clang++`, and `CXX` environment variables from CI workflows. In `.github/workflows/ci.yml`, the `build-32bit` job removes `g++-multilib` from the `apt-get install` line. The `build-centos` job removes `gcc-c++` from the `dnf -y install` line. The `build-old-chain-jemalloc` job removes `g++-4.8` and the `update-alternatives` line for `g++`. In `.github/workflows/daily.yml`, similar changes are made across 13 distinct job definitions, including the FreeBSD job which removes the `CC: clang` and `CXX: clang++` environment variables entirely.

The `.gitignore` change removes the line `deps/fast_float/libfast_float.a`, which is correct since the static library is no longer built. The `deps/Makefile` change removes the `fast_float` target, its `.PHONY` declaration, and its entry in the `distclean` rule. The `src/Makefile` changes are comprehensive: `fast_float` is removed from `DEPENDENCY_TARGETS`, `-lstdc++` is removed from `FINAL_LIBS`, the `-I../deps/fast_float` include path is removed from `FINAL_CFLAGS`, and `../deps/fast_float/libfast_float.a` is removed from the redis-server link line. Additionally, `fast_float_strtod.o` is added to `REDIS_SERVER_OBJ`.

I verified that no residual references to `g++`, `libstdc++`, `deps/fast_float`, or `libfast_float.a` remain in the changed files. The `deps/fast_float/Makefile` and `deps/fast_float/fast_float.h` files are fully deleted (deleted file mode 100644). The `deps/fast_float/README.md` and `deps/fast_float/fast_float_strtod.cpp` and `deps/fast_float/fast_float_strtod.h` are also fully deleted.

One note: the FreeBSD job in `daily.yml` previously set `CC: clang` and `CXX: clang++` as environment variables. After this PR, neither is set. The job will use the system default compiler, which on FreeBSD is typically `clang`. Since Redis no longer requires `CXX`, removing `CXX: clang++` is correct. However, if the FreeBSD system default `CC` is not `clang` (unlikely but possible), the build could fail. This is a minor concern.

The `sort.c` change removes the inline `fast_float_strtod` call and replaces it with `string2d()`, which means `sort.c` no longer directly depends on `fast_float_strtod.h`. However, `sort.c` may still transitively include it through other headers. This is not an issue but worth noting for code hygiene.

## Testing Gaps and Recommendations

The `fastFloatTest` function in `src/fast_float_strtod.c` provides good coverage of the fast path, edge cases, and fallback behavior. It includes 6 test categories: (1) finite decimals covering basic values, signs, leading zeros, decimal points, scientific notation with positive/negative exponents, and boundary values like `9007199254740992` (2^53) and `9007199254740993` (2^53+1); (2) invalid decimal inputs with trailing junk, missing exponents, and malformed signs; (3) valid inf inputs including `inf`, `INF`, `Inf`, `infinity`, `INFINITY`, `Infinity`, with signs; (4) invalid inf inputs like `in`, `infin`, `info`; (5) valid nan inputs including `nan`, `NAN`, `Nan`, and `nan(n-char-seq)` variants; (6) invalid nan inputs with unclosed parentheses, invalid characters, and trailing garbage. The test also includes a large-input test that exercises the `zmalloc` fallback path (input > 128 bytes).

The SORT regression test in `tests/unit/sort.tcl` adds a specific test for the smallest normal double `2.2250738585072012e-308`, verifying that `SORT BY weight_*` produces the correct ordering. This is an important boundary test that catches precision issues near `DBL_MIN`.

**Missing test scenarios:** (a) There is no test for hexadecimal input (`0x10`) in the `fastfloat` unit test, although the test case `{"0x10", 16.0}` exists in `decimal_ok[]`. Wait—upon re-reading, `0x10` is in `decimal_ok[]` with expected value `16.0`, and `run_ff_tests` with `expect_failed=0` expects success. This exercises the `strtod` fallback path for hexadecimal. Good. (b) There is no test for locale-dependent behavior (e.g., a locale where the decimal point is `,` instead of `.`). Since Redis always uses the C locale, this is acceptable, but a defensive test would be valuable. (c) There are no tests for extremely long mantissas (e.g., 100+ digits) to verify that the fast path correctly rejects them and falls back to `strtod`. (d) There are no tests for the interaction between the `endptr` return value and the length parameter—for example, parsing `"3.14 extra"` with `len=4` should succeed and return `endptr` pointing to the space. (e) There are no tests for empty strings or strings containing only whitespace. (f) There are no tests for very large negative exponents (e.g., `1e-1000`) that would trigger the `strtod` fallback and potentially produce underflow. (g) The `resp_parser.c` change removes the `MAX_LONG_DOUBLE_CHARS` length check for the new API, but the guard `if (len <= MAX_LONG_DOUBLE_CHARS)` still prevents excessively long inputs. A test verifying that RESP doubles exceeding `MAX_LONG_DOUBLE_CHARS` are handled correctly (returning 0) would be valuable.

**Recommendations:** (1) Add a dedicated test for `string2d()` with hexadecimal inputs to verify the behavioral change. (2) Add tests for the `endptr` return value at all call sites. (3) Add tests for the 32-bit x86 extended-precision workaround (if CI includes 32-bit builds). (4) Add a test for `nan(ind)` and `nan(snan)` variants, which MSVC can produce. (5) Consider adding a fuzz test or property-based test that compares `fast_float_strtod` output against `strtod` for a large number of random inputs.

## Actionable Recommendations

**Must address before merge:**
1. Verify that the `string2d()` behavioral change (removing the `strtod` fallback for unconsumed input) does not break any existing tests or use cases. Run the full test suite with particular attention to `SORT`, `ZADD`, `ZRANGEBYSCORE`, and any command that parses floating-point scores.
2. Verify that the `0x10` test case in `decimal_ok[]` actually passes—this depends on the `strtod` fallback path being invoked and consuming all 4 characters. If the fast path's `parse_number_string()` function does not recognize `0x` as a valid prefix, it should return 0 and trigger the fallback.
3. Confirm that the FreeBSD CI job still builds correctly after removing `CC: clang` and `CXX: clang++` environment variables.

**Should address:**
4. Add a test case for `string2d()` with hexadecimal input to document the expected behavior.
5. Add test cases for the `endptr` return value, particularly for inputs with trailing whitespace or garbage.
6. Add a comment in `fast_float_strtod.c` explaining the `zmalloc` dependency and its implications for non-Redis reuse.
7. Add a test for extremely long mantissas (100+ digits) to verify fallback behavior.

**Nice-to-have:**
8. Add a fuzz test or property-based test comparing `fast_float_strtod` against `strtod` for random inputs.
9. Add a benchmark comparing the new C implementation's performance against the old C++ `fast_float` library.
10. Consider abstracting the `zmalloc` dependency behind a macro or function pointer for portability.
