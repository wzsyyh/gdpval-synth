# Code Review: elastic/elasticsearch#140645

## Executive Summary

**Executive Summary**

Based on a thorough technical review, this PR receives a **no-go recommendation** for merge into the main Elasticsearch codebase. While presented with a humorous tone, the proposed changes lack a substantive technical foundation and do not align with the project's standards for contributions to core query language functionality.

The PR introduces a novel `CHICKEN` function to ES|QL, purported to wrap text in ASCII art of a chicken. The implementation consists solely of a generated evaluator class (`ChickenEvaluator.java`) and a changelog YAML file. The evaluator's code, as generated, does not represent a valid or integrated expression function within the ES|QL execution framework. It appears to be a placeholder or template output, missing the necessary class extensions, method signatures, and integration points required for a callable ES|QL function. Furthermore, the PR lacks any corresponding unit tests, integration tests, or functional specification that would allow for validation of its behavior or ensure its stability.

The primary objections are threefold. First, the function serves no analytical, operational, or data-manipulation purpose within the context of ES|QL, which is designed for efficient data exploration and processing. Second, the proposed change violates the project's contribution guidelines, which require that all features and modifications have a clear, documented use case and technical benefit for the user community. Third, the implementation is incomplete; it does not handle input validation, error cases, or integrate with the expression tree planning and optimization layers. Introducing such a change would create technical debt and set a non-viable precedent for future contributions.

Therefore, while the creative intent is noted, this PR is not suitable for inclusion in Elasticsearch. We recommend the contributor review the project's contribution guidelines and engage with the community through designated channels (e.g., GitHub issues, forums) for future ideas that align with the project's roadmap and technical goals.

## PR Overview

# PR Overview: elastic/elasticsearch#140645

This PR introduces the `CHICKEN` function to the Elasticsearch Query Language (ES|QL). As described in the pull request, the function is intended to wrap any text message in ASCII art of a chicken. The proposal stems from casual discussions and represents a novelty addition to the query language. The PR modifies two files: a changelog entry (`docs/changelog/140645.yaml`) and introduces a new generated evaluator class (`ChickenEvaluator.java`). The function's stated purpose is to transform input strings into a formatted, chicken-themed ASCII art representation within query results.

From a technical standpoint, the implementation raises several concerns. The `ChickenEvaluator.java` file is located within the `generated` source directory, suggesting it is intended to be auto-generated code, yet the PR appears to commit it directly. The provided code snippet is incomplete, focusing only on the ASCII art generation logic without showing the necessary ES|QL integration, registration, or evaluation framework hooks. The function lacks any formal parameter type validation, error handling, or tests, which are mandatory for any new expression in the ES|QL engine. Furthermore, adding a purely decorative string transformation function sets a problematic precedent for the query language, which is designed for data retrieval and analysis, not cosmetic output formatting.

Overall, while the PR aims to bring a lighthearted feature to ES|QL, it does not meet the engineering standards for inclusion in the Elasticsearch codebase. The change is functionally incomplete, bypasses code generation pipelines, and introduces a concept that does not align with the core use cases of the query language. It lacks the rigorous testing, documentation, and integration required for a new public-facing function.

## Files Changed

The `docs/changelog/140645.yaml` file correctly follows the Elasticsearch changelog format but introduces a category that may not align with the project's established conventions. The file uses the `"Fun"` type under `"features"`, which, while thematic, deviates from the standard `"Feature"`, `"Bug"`, or `"Enhancement"` types typically used. For consistency and to ensure proper downstream processing, this should be revised to a standard type such as `"Feature"`. The metadata, including the PR number and contribution details, is properly formatted.

The primary implementation resides in the auto-generated `ChickenEvaluator.java`. While the generated code functions as specified, the core logic for ASCII art construction is suboptimal. The current implementation performs multiple, sequential `String.concat()` operations within a hot path, which is inefficient. This should be replaced with a single, precomputed constant or a `StringBuilder` to avoid intermediate object creation and improve performance, as is standard practice in generated evaluation code.

Furthermore, the evaluator's `process()` method correctly returns the concatenated `StringBlock`, but the ASCII art template is embedded directly in the evaluation logic. This couples the presentation layer with the computation, making the art difficult to modify or localize. A cleaner separation would be to define the chicken ASCII template as a static constant, improving maintainability. The generated boilerplate (e.g., the `Factory` class and `Evaluator` registration) appears correct, assuming the generator inputs are valid.

## Code Quality Assessment

## Code Quality Assessment

The generated `ChickenEvaluator.java` follows the established patterns for ES|QL expression evaluators, leveraging the code generation framework correctly. The core logic for wrapping text in ASCII art is contained within a single, static `doEvaluate` method, which is a positive architectural choice for testability and separation of concerns. However, the readability is impacted by several factors. The method handles whitespace normalization by replacing all internal line breaks with a single space before processing. While functional, this transformation is implicit and could be surprising to maintainers; a comment explaining the rationale would improve clarity. Furthermore, the ASCII art template is embedded as a long string literal with escape sequences, making the output format difficult to verify at a glance. Extracting this constant to a separate resource file or at least a class constant with a clear name would enhance maintainability.

A critical deficiency is the complete absence of unit tests for this new functionality. A core PR like this must include comprehensive test coverage to validate behavior across a spectrum of inputs. The current submission provides no verification for the happy path, nor for essential edge cases. Without tests, we cannot assert correctness, prevent future regressions, or safely allow other developers to modify this code. The test suite should explicitly cover: normal single-line strings, strings containing the `\` character (which could interfere with escape sequences), empty string inputs, and strings with leading/trailing whitespace. Performance testing with exceptionally long strings should also be considered to ensure the evaluator does not introduce significant latency or memory pressure.

Several important edge cases are unaddressed in the implementation. The function’s behavior for a `NULL` input is unclear from the provided code; it should explicitly handle `null` to avoid propagating nulls or throwing unhandled exceptions. The current whitespace normalization aggressively collapses all internal whitespace (including tabs and multiple spaces) into single spaces, which may not be a desirable or documented behavior. Additionally, the ASCII art has a fixed width, and no logic exists to handle or truncate input messages that exceed this width, which would break the intended visual output. These ambiguities and missing guards must be resolved before merging.

## Security & Performance

The proposed CHICKEN function introduces measurable security and performance concerns that must be addressed before it can be considered for production use. From a security perspective, the primary risk lies in the unsanitized string manipulation inherent in the ASCII art generation within `ChickenEvaluator.java`. This function processes arbitrary user-provided text from ES|QL queries. If the implementation relies on naive string concatenation or formatting without strict input validation and escaping, it could become an avenue for injection attacks, particularly if the resulting "chicken" output is ever logged, rendered in a web UI, or used in further processing. An attacker could potentially inject control characters or malicious payloads designed to exploit downstream systems that consume the ES|QL output.

Performance impact must be evaluated at scale. The generated evaluator performs multiple string operations, line-splitting, and concatenation for every invocation. In a distributed system like Elasticsearch, where functions may be evaluated over millions of documents, even minor per-operation overhead can significantly degrade throughput and increase latency. The use of fixed-length ASCII art templates also implies a variable but substantial increase in data volume per document, which could adversely affect network traffic between nodes, memory usage during result set assembly, and overall cluster scalability. The implementation should include benchmarks comparing query latency and resource utilization with and without the function under a representative workload.

The current implementation appears to prioritize feature delivery over operational safety. We recommend adding robust input validation and size limits directly within the evaluator to mitigate injection risks and contain payload expansion. Furthermore, a performance assessment with realistic data volumes is essential to quantify the throughput cost before merging this into the codebase.

## Recommendations

**Recommendations**

While the novelty of the CHICKEN function is clear, this PR requires significant revisions to meet production standards. The primary technical concern is the use of a **generated code file** (`ChickenEvaluator.java`) as the primary implementation. Generated code from the ES|QL pipeline is a build artifact, not a hand-written source file. Checking it in directly bypasses the critical code generation and validation steps, creating a maintenance burden and potential version conflicts. The implementation should instead be defined in the appropriate source template and generated through the standard build process.

Furthermore, the PR lacks the necessary integration for a first-class ES|QL function. A new function must be registered in the `EsqlFunctionRegistry`, have its type resolution and parameter validation properly defined, and include corresponding unit and integration tests. The current implementation appears to operate outside the core expression evaluation framework, which is inconsistent with the architecture of the ESQL engine. The ASCII-art formatting logic, while creative, would be better encapsulated as a utility separate from the evaluator's core responsibility of data transformation.

Finally, this PR raises a process question. If this is intended as an experimental or humorous contribution, it should be explicitly labeled as such (e.g., prefixed with `[EXPERIMENTAL]` or filed under a distinct non-production module) to set correct expectations and avoid diverting core review resources. For a genuine contribution, the scope should be narrowed: remove the generated code, provide a minimal, well-integrated function implementation, and follow the established checklist for adding new functions, including documentation and tests that align with Elasticsearch’s quality standards.
